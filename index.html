How rarity scoring works (0–99)
  • Base score by length — 3 chars = 64 down to 16 chars = 9. Short IDs are the rarest commodity.
  • Bonuses: 3-letter dictionary word +24, longer words +9/+13/+14, real first name +7…+18, meaningful acronym +8, pronounceable +8, OG style +5, notable repeats +3…+7, letter patterns +5, balanced vowels +3.
  • Penalties: digits −18, underscores −14, hyphens −12, hard to pronounce −10/−14, rare-letter clusters (q/z/x/j) −4 each (waived for real words, names and intentional keyboard patterns).
  • Tiers: 90–99 S, 80–89 A, 70–79 B, 60–69 C, below 60 Common.
How availability is verified
Verification posts to Sony's account-creation service (accounts.api.playstation.com) with reserveIfAvailable:false, which never claims or reserves the ID: 201 = claimable (double-confirmed on separate requests), 400/3101 = account exists, 400/3208 = Sony-blocked word, 406 = reserved class (empirically every 3- and 4-character ID — Sony no longer issues them; the listed catalogue is 5+). Scope note: this is the validator the web account-signup uses; the PS App / console rename flow applies an additional stricter word-policy layer and can reject an API-available ID. Entries not yet verified show Unknown — no guesswork — and the server's background scan works the queue automatically (≈1 per 0.5s plus live search; 60s cooldowns on any throttle). New verifications stream into the open page via the Sync menu, and rebuild with python3 build.py to bake them into the portable file.
Live search: serve the app with python3 server.py and search any valid ID — if it isn't verified, the app asks the included server, which checks Sony exactly like the sweep (browsers can't call Sony's endpoint directly: it rejects any request carrying an Origin header) and writes the result to data/verified_live.json, so the name becomes a permanent database row on the next rebuild. Sony calls are rate-limited (≈1 per 1.6s) and share headroom with the running sweep.
